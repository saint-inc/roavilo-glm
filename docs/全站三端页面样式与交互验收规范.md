# roavilo 全站三端页面样式与交互验收规范

请对 roavilo 网站进行全面核对和调整，目标是：

**除网站 Logo / 品牌标志由 dianping 替换为 roavilo 外，其余所有用户可见的页面效果、视觉样式、布局结构、响应式表现和交互行为，都要求与 dianping.com 完全一致。**

这里的“完全一致”不是“风格类似”或“参考实现”，而是要求进行 **1:1 对照还原**。

> **不要理解成“仿 dianping.com 风格”，我要的是“除 Logo 外，前端表现 1:1 一致”。**

消费者订单页与商家订单页的三端交互必须读取同一批订单项目状态：消费者页面聚合展示整单及各项目商家，商家页面只展示当前商家的项目；券码、地址、包裹、退款和履约状态在两侧更新后必须一致，不能用独立 Demo 副本形成只在视觉上连通的页面。

三端页面应展示面向用户的订单号、券码或履约号，不得把 `users.id`、`merchant_users.id`、`merchant_id`、`order_items.id` 等内部数据库主键当作公开业务编号；响应式布局变化也不能改变这一数据可见性边界。

每个 Host 在桌面、iPad 和手机尺寸都只能加载自己的 JavaScript 入口：Main/国家市场为 `main.js`，Merchant 为 `merchant.js`，企业/开发者域为同名入口，多级域按目录嵌套。验收时应在页面源码或 Network 中确认没有其他 Host 的入口脚本；共享模块只能作为当前入口依赖出现，不能由 Blade 作为全站脚本额外加载。

## 具体要求

包括但不限于：

- 页面整体布局必须一致
- 页面宽度、高度、边距、留白、间距必须一致
- 信息密度必须一致
- 页面背景颜色必须一致
- 模块背景、卡片样式必须一致
- 字体大小、字号、字重、行高、文字颜色必须一致
- 标题、正文、辅助文字的层级必须一致
- 边框、圆角、阴影、分割线必须一致
- 图标的尺寸、位置、间距必须一致
- 按钮的尺寸、颜色、圆角、字体、状态必须一致
- 输入框的尺寸、边框、占位文字、Focus 效果必须一致
- 下拉框的样式、展开位置、动画、选中效果必须一致
- 多选、单选、Checkbox、Radio 的样式和交互必须一致
- 日期选择器、人数选择器、城市选择器必须一致
- 筛选区域的布局、顺序、样式、展开方式必须一致
- 弹窗、浮层、Drawer、Popover、Dropdown 必须一致
- Hover、Focus、Active、Selected、Disabled 状态必须一致
- Loading、Skeleton、Empty 状态必须一致
- Tab、Carousel、分页、滚动、Sticky 等行为必须一致
- 受控季节活动页必须在 1440px、820px、390px 下验证首屏信息层级、优惠卡密度、空状态和跨市场 404，不能以宽泛活动模板掩盖未登记 path
- My dianpings 必须同时验收 All/Ready/Failed/Received/Gifted、最新/最旧排序、空列表和手机横向 Tab；通知列表必须检查跨账户不可见
- 商家单券核销必须分别验收输入、预览、取消、过期、确认、重复和并发失败状态；预约必须验收容量下限、时段开关、改期回滚、取消释放和事件历史
- 消费者站与商家中心必须验收同一条 dianping 式业务链：商家活动草稿/审批/上线、消费者同规格价格与库存、预付订单回流商家、预约或核销、消费者状态回写、退款、核销后佣金和打款；不得用两套互不相干的页面或 Demo 数据通过视觉验收
- 上述跨端验收必须实际提交测试流程并断言数据库状态变化，至少覆盖发布、审批、购物车、五步结账、订单归属、核销前余额为零、核销后佣金/余额及消费者状态回写；每次相关代码变化后都要重新执行，页面截图、链接可点击、HTTP 200 或上一次通过记录均不能替代本次业务闭环测试
- 实物结账必须在1440px、820px、390px分别验收动态 Shipping 步骤：每个项目地址字段、错误提示和复核摘要不能串项；订单详情的逐项目改址在发货前可编辑、发货后清晰锁定；Merchant 发货多选框必须显示履约项目号而不是把消费者父订单号误作商家编号
- 消费者—商家集成发布前除核心闭环外还必须执行全量 PHPUnit、Pint、Vite 生产构建、路由重复检查和差异格式检查；自动化全绿只证明仓库已实现流程，真实支付、OAuth、消息、地图、存储和连接器仍须用正式 Sandbox/生产前账号分别验收
- 混合订单必须在消费者购物车、结账、订单列表、订单详情、电子券和退款页逐项目显示履约商家；商家订单页必须区分购买账户与实际收件人，并只显示当前商家的项目。桌面表格、iPad 和手机横向表格均要验收多商家长名称、多个消费者、礼品收件人与邮箱/电话换行，不能因响应式收敛隐藏归属信息
- 与 dianping 当前行为一致，混合订单还要在三端逐项目展示或操作不同商家运费、取消和收货地址；Getaways 酒店预订不得混入普通购物车。任何“整单操作”必须明确作用范围，不能让用户误以为会同时修改另一商家的履约项目
- 同一消费者订单出现多个 `merchant_id` 时，界面不得把商家列表压缩成含糊的单一“卖家”字段；应在每条项目旁标识对应商家，并保证商家端只渲染当前商家的明细子集
- 商家活动列表的消费者商品页入口必须打开该活动所属国家 Main Host 的同一活动；桌面、iPad 和手机都要检查跨 Host 返回、库存变化、暂停/下架和未知活动真实 404
- 动画时间、动画方式、过渡效果必须一致
- 鼠标操作效果必须一致
- 手机和平板上的触控效果必须一致
- PC、iPad、手机端的响应式布局必须一致


## 不允许自行发挥

不要自行重新设计，不要进行“优化风格”，不要加入 dianping.com 没有的效果，也不要删除 dianping.com 已有的视觉或交互细节。

请把 dianping.com 作为唯一的 UI 和交互标准。

## 执行方式

消费者与商家页面都必须使用与 dianping 对应页面一一映射的完整 Host 标签和 URL path 成对打开，只替换根域；不得通过改路径、合并子域或跳转到另一页面规避视觉与交互对照。roavilo 补充闭环页面单独验收，并在 URL 清单标明其没有 dianping 原路径。

URL path 中出现的 `dianping` 字样仍属于地址契约，不能因页面可见品牌已改为 roavilo 而改写 path。三端对照必须在相同 path 和查询参数下进行；历史误建的 roavilo 品牌化别名只允许单跳到来源原路径，不能反向把原路径规范化为 roavilo 自定义路径。

路径审计必须先记录来源链接和最终 URL，再开始三端视觉对照。来源站自身发生的跨 Host 跳转应在 roavilo 做等价跳转；来源最终 URL 保持不变时，roavilo 不能先跳到 `/category/*`、`/account/*` 或其他自定义路径后再验收，否则即使页面视觉相似也视为 URL 验收失败。

`us/uk/sg/hk` 等市场国家 Host 需要分别按对应市场页面成对验收，但实现继续复用 `Main` 页面与状态机；市场差异由受控市场配置驱动，不复制四套业务目录。独立业务 Host 和多级业务 Host 则按自己的单层或嵌套目录逐页验收。

执行时必须同时打开：

1. dianping.com 对应页面
2. roavilo 对应页面

在相同窗口尺寸、相同设备尺寸下逐区域比较。

### 必须纳入三端验收的页面链路

- 消费者购买后链路：订单列表、订单详情、独立兑换券、核销状态、已兑换项评价及重复提交错误状态。
- Help Center：`/help` 单跳、`/faq` 首页、搜索结果、分类、文章、空结果、订单关联客服会话和未知文章 404。
- 开发者公开页：`/developers*` 总览、指南、支持、API 目录、政策和申请状态，`/developers-docs/*`、`/developers-api/*` 的白名单详情，OpenAPI 文件下载及未知 slug 404；表单必须检查必填、邮箱、同意、成功追踪和重复提交反馈。
- Main 公司内容：`/articles/about`、`/articles/team`、`/articles/dei`、`/articles/press`、`/articles/news` 与已发布新闻详情必须在原 Host/path 直接渲染，不能用 About/Press 跨域跳转规避对照；同时验收空新闻和未知 slug 404。
- 公开商家营销页：`/merchant/business-resources`、`/merchant/booking-solutions`、商家条款和商家隐私路径，以及行业、绩效、伙伴、案例和资源页面；邮件确认与咨询表单必须覆盖正常、验证失败、未同意、追踪编号和移动端键盘/焦点状态。
- 商家中心：工作区选择、草稿、活动详情、连接器、预约、赞助活动、洞察、建议、客服、收件箱和登出；同时检查 owner/admin/manager 不同权限下的隐藏、禁用和 403 状态。
- Enterprise Hub：公开首页、Google SSO 未配置 503、未登录工作区导向、已登录多商家/多币种看板、无权工作区。
- 企业公开站：Investor 资料筛选、Privacy 政策参数、About/Press 详情、Careers 团队/地点/员工故事/洞察及职位筛选。
- 兼容域只验证状态码、`Location`、path/query 保留、单跳与退役 410，不对跳转源 Host 伪造一张可视业务页面。

对每个上述链路，至少验收正常、加载、空数据、验证失败、无权和未匹配 404 状态；不能只检查首页或导航存在。

- 颜色差异
- 圆角差异
- 阴影差异

不要只检查静态页面，还必须检查所有交互状态。

## 最终验收标准

**如果把 dianping.com 和 roavilo 的 Logo 都隐藏掉，只看页面本身，用户应该无法通过页面风格、样式、布局或交互效果判断哪一个是 dianping.com，哪一个是 roavilo。**

唯一允许明显不同的地方是：

**dianping.com Logo → roavilo Logo**

除此之外，网站的视觉、样式、布局、交互、动效和响应式表现都按照 dianping.com 进行 1:1 还原。

## 其他要求

同时注意：不要破坏 roavilo 现有接口、数据、业务逻辑和路由。

Git 分支合并或清理不得作为省略三端验收的理由。如确有功能分支并入 `main`，删除分支前必须确认其用户可见页面及交互已纳入本文对应的桌面、iPad 和手机回归矩阵。

## 商家中心外壳与稳定路径验收

- 商家首页、Payments、Support、Reports、Inbox 和五个 `/manage/*` 标签必须在 1440px、820px、390px 分别检查侧栏/抽屉、顶部快捷操作、内容表格、页面导览和专用页脚；直接访问稳定 URL 不应发生 301 或丢失当前标签。
- 页面导览使用可键盘展开的 `details/summary`，展开后步骤编号、正文和焦点不能被顶部栏遮挡；手机宽度必须退化为单列。
- Support 的 Chat、Email、Phone 卡片在供应商未配置时必须明确显示不可用，Email 应能滚动到可追踪工单表单；不得用无响应按钮伪装在线客服。
- 商家页脚四列在 iPad 收敛为两列、手机收敛为一列，所有帮助、App、资源和法律链接都必须到达已实现页面或明确的安全失败页，不允许 404。
- App 卡片和页脚入口必须保留 `/mobile` 网页功能；Android/iOS 尚未开发时要显示真实状态，不能伪造可下载安装。
- 本轮临时 Artisan 入口已确认商家登录页实际加载 `merchant.css`，1440px、820px、390px 均无水平溢出。XAMPP 默认 `*.localhost` 当前指向 XAMPP Dashboard，配置正确 VirtualHost 前不能把该地址的 200 响应当作 roavilo 页面通过。

## Host 样式入口隔离

- `roavilo.com`、`www.roavilo.com` 和全部国家市场 Host 只加载 `main.css`。
- `merchant.roavilo.com` 只加载 `merchant.css`；Investor、About、Privacy、Press、Careers、Enterprise 与 Developers 分别加载自己的同名入口。
- `docs.developers.roavilo.com` 使用与 Host 层级一致的 `developers/docs.css`，后续多级域也必须按相同目录规则建立入口。
- `base.css`、`shared/ui.css`、`shared/corporate.css` 只保存确实共用的基础规则，并作为当前 Host 入口的构建依赖；页面不得直接加载这些共享文件。
- 禁止把全部 Host 样式重新合并为 `app.css` 或其他全站入口。每次新增或移动选择器都要检查它只存在于责任 Host 或明确共享模块，并在 1440px、820px、390px 下确认页面没有横向溢出或断点回归。
